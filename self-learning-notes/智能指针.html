需要注意的是，C++标准对引用提出了以下三点硬性要求，在使用时一定要加以注意：

  1. 必须初始化：int &ref; 是编译错误。不存在“空引用”，因此省去了指针判空（if (ptr != nullptr)）的麻烦。

  2. 不可重新绑定：引用一旦绑定到 a，其终身指向 a。执行 ref = b; 并不会让 ref 改指向 b，而是把 b 的值赋值给 a。这也意味着引用的指针是不存在的（即int&*），因为引用不是对象。

  3. 不延长生命周期：返回局部变量的引用依然是悬挂引用（未定义行为），引用本身不管理内存所有权。

事实上，引用与指针在汇编层面没有区别，是指针的一个语法糖。你可以理解为，引用只是C++编译器对一个常量指针作了一些封装，使得其可以自动完成取地址、解引用的功能，上文中引用区别于指针的特性都是编译器约束完成的，一旦编译成汇编就和指针一样。由于引用只是指针包装了下，所以也存在风险，比如如下代码：

3. 左值与右值

前文提到，引用一般特指为左值引用。有左值就肯定有右值，那么这两者之间又有什么区别呢？

从定义上很好区分这两者：

  • 左值：拥有持久的内存地址，可以取地址（&），生命周期由变量作用域决定。

  • 右值：没有持久内存地址的临时值，要么是字面量（如 5），要么是计算过程中的中间结果（如 a + b），要么是函数返回的临时对象，当前语句结束后即被销毁。

换句话说，就是“能取地址的就是左值，不能取地址的就是右值”。

4. 右值引用

引入右值引用的原因可以从下面这个例子中直观体现——

众所周知，std::vector是一个非常方便的STL容器，它的长度可以灵活调整，我们随时能够通过push_back操作往容器中添加新的元素，同时使它的长度发生改变。

但是，前面我们提到过，程序中的所有数据都会存储在内存当中（当然，学习完左值和右值之后，我们应该明白这些数据不会包括右值）。从这一点出发，我们不妨考虑一下std::vector的实现方式：它里面的数据应当如何存储呢？

一种直接的想法是，每当我push_back一个新的元素时，就为它申请一块新的内存空间用于存储，同时在前一块内存空间中记录它下一块内存空间的地址信息。但显而易见的是我们此时设计出了一个链表，并不能满足std::vector的随机访问的需求。

要想随机访问必须保证数据存储的连续性，但根据前文所述，即便是使用new T[]，也只能申请连续num块内存空间，但num作为预先就确定下来的常量，显然不能保证一定能满足std::vector无限延伸的需求，且如果num的值过大而需要用到的空间又不大的话，又会产生空间上的浪费。

由此自然产生的想法就是，我们每次一开始申请的时候，都只申请一小段连续内存。当连续内存不够用之后，再申请一段更长的连续内存（一种常见的做法是原内存长度的2倍），将原来的数据全部搬运到新的连续内存当中，再把老的连续内存全部释放掉。这样做既保证了访问的随机性，也保证了能随时往里面添加新的元素。

看上去一切都非常完美，但有一个重要的问题却被我们忽略了：应该如何高效搬运数据？

最常用的方式肯定是拷贝构造，它也的确能够完成我们需要的搬运工作。

然而拷贝构造是一个非常缓慢的过程，而且原内存中的数据在本次拷贝之后将不再有任何作用，被立即释放。专门拷贝一份不需要的数据显然是毫无必要的，正如我们在同一个电脑磁盘内搬运某个大文件时，显然不需要先将这个文件拷贝到新的地址，再将原地址上的该文件删除，只需要进行剪切操作，也就是目录索引位置的转移即可，这种方式显然更加迅速。

揆诸std::vector的例子亦是如此，我们希望设计一种全新的搬运方式，使得数据的搬运不再是繁琐的拷贝+删除，而是像剪切操作那般只发生所有权的转移。这就是移动构造。

这种错误很好避免，只需要在解引用前加上指针判空（if (ptr != nullptr)）就能避免对野指针的解引用（当然我们一般尽量避免直接定义一个野指针，对所有指针都进行初始化，指针判空一般用于使用完以后的指针），同时在释放内存的同时立即将指向该内存的指针置空就能避免对悬空指针的解引用。

但普通指针在内存管理上存在更大的缺陷。

第一，前文提到了，对于普通指针而言，使用new分配的内存必须用delete进行显式释放，否则会造成内存泄漏（Memory Leak），例如：

在这个例子中，new int分配了一块新的内存，交给ptr管理（仅由它指向这块内存）。但是后来我们对ptr指针进行了修改（让它指向了nullptr或是其它地方），导致这块内存不再被任何指针指向，程序运行结束后也就无法将这块内存进行释放（计算机根本不知道这块内存的存在），造成内存泄漏。

任老师上课就分享过这样的例子：有一个交通摄像头在工作了一周之后突然无法使用了，检查之后才发现是一处new的内存没有delete，导致摄像头每次工作时都会分配出一块无法被释放的内存，最终导致数据占满了整个内存使得程序根本无法工作。由此可以一窥内存泄漏的风险。

第二，一块内存还有可能会被双重释放（Double Free），造成段错误或内存破坏：

或许这些错误看上去都是可以通过极致的细心来规避的，但如果程序在new和delete之间抛出异常而终止了呢？程序在退出的时候，普通指针不会自动调用delete来释放内存，依然会造成Memory Leak，这是不可避免的。

因此，C++11引入了智能指针。智能指针依据RAII思想，对普通指针加上了一层包装，用有生命周期的对象来自动管理指针的内存，即在对象创建时自动申请内存，在对象被析构时自动释放内存，既能避免管理者手动操作时new以后忘记delete的情况，也能避免因程序异常导致内存未被释放的情况（因为在异常退出后，管理指针的智能指针对象被析构，连带着内存也被立即释放）。

其实严格意义上讲，早在C++98当中就已经有了智能指针的雏形auto_ptr，但由于它的拷贝构造和赋值操作会转移所有权，源对象会被置空，既不符合传统复制语义，又不能放入各种标准容器，同时还不支持数组指针，因此在C++11当中被标记为已弃用，并在C++17中被正式移除。

本次大作业，我们需要实现三种智能指针，分别是unique_ptr、shared_ptr、weak_ptr，它们各有特点，下面一一介绍。

2. unique_ptr

显然，unique_ptr具有uniqueness，即它拥有它所指向对象的唯一所有权。这是最基础的一种智能指针，通过将unique_ptr的生命周期和它绑定的对象内存的生命周期进行强绑定，实现对内存的自动管理。

在任何时候，unique_ptr都不能接受拷贝构造，只允许通过移动构造来转移对象的所有权。因此，在unique_ptr的实现中，我们必须显式删除拷贝构造和拷贝赋值方法，同时设计出移动构造和移动赋值的方法，还要始终牢记当对象（通过operator=或reset等方式）被其它指针接管时，原有对象的unique_ptr必须立即被删除。

3. shared_ptr

显然，一个对象只能被至多一个指针管理在实际工程应用中过于严苛，也使得引用传递等基本功能的实现变得更为复杂（需要先从A将对象所有权转移给B，等B用完以后再还给A）。可是unique_ptr的设计思路是“一损俱损”，指针销毁直接会导致内存释放，这强制要求了指针和对象之间必须建立双射关系。所以，这种思路不能直接应用到多个指针管理内存空间之上。

如何使用智能指针的思路来解决这一情况呢？一个自然的想法就是使用一个内置计数器，实时计算每个对象被多少个智能指针同时管理。当一个新的共享智能指针被创建时，将计数器的值置为1（只有自己在管理），随后在拷贝和析构时进行相应的增减。当计数器清零时，自动释放它管理对象的内存空间。这种计数方式称为强引用计数shared_cnt，这种智能指针的设计称为shared_ptr。

4. weak_ptr

shared_ptr的设计看起来很美好，但学过oi的同学想必能一眼看出它的潜在隐患。我们可以用算法竞赛中的拓扑排序进行类比（没学过也不要紧，大一下学期的算法课上你们就会接触到这个算法了）。shared_ptr释放对象内存的时机是shared_cnt归零的那一刻，其实就像是拓扑排序算法中将每一时刻入度归零的所有点放入拓扑序中，两者的操作是很相似的。

但众所周知，拓扑排序只能在DAG上成立，倘若有向图中成环，那么环上所有点的入度都不可能减到0，也就意味着环上的所有点都无法被放入拓扑序中，拓扑排序就失效了。

揆诸shared_ptr亦是如此。倘若我们用shared_ptr实现一个双向链表或有环图，那么在析构的过程中，也会发生如有环图拓扑排序这样的情况，导致环上指针管理的内存无法释放，同样会造成内存泄漏。这种风险就是循环引用。我们以一个双向链表的实例为例：

问题的原因在于两个智能指针的相互管理，但从这个实例中我们可以发现，在使用中相互管理是不必要的，只需要指针A管理指针B就能保证链的完整性，而指针B要想回到指针A时，无需通过管理的途径，只需要能够观察到A的位置即可。这就是weak_ptr的实现思路。

通俗来讲，weak_ptr就是shared_ptr的一个弱化版本或是补丁。它持有一个非拥有（“弱”）引用，指向由shared_ptr管理的对象，起到观察者的作用，一方面观察有多少shared_ptr指向被管理的对象，一方面管理控制块的生命周期（而不管理对象本身的生命周期，即不会使得shared_cnt发生变化）。对weak_ptr的引用计数称为弱引用计数weak_cnt，它与shared_cnt被同时维护，且两者的计数方式是相互独立的。

如果你看过去年的阅读材料文档，会发现有这样一句话：当shared_cnt减为0时，weak_cnt-1。但这条规则实际上是错误的。weak_cnt和shared_cnt之间不会有任何相互影响，因为它们管理的东西是完全不同的。

为了同时维护两个数值，并实现强引用计数对对象的管理和弱引用计数对控制块的管理，往往将两个计数器和被管理的对象用一个控制块（Control Block）进行统一维护。

由于weak_ptr本身不能创建新的对象（前文已经提到，它指向由shared_ptr管理的对象），所以Control Block的创建只能由shared_ptr创建。因此，在一个Control Block被新建时，两个计数器的初始化值一定是shared_cnt = 1（代表创建它的shared_ptr），weak_cnt = 0（当前没有任何观测者）。

Control Block被析构的时间节点为shared_cnt == 0 && weak_cnt == 0，代表控制块中被管理的对象内存已经被释放，同时没有任何weak_ptr在观测这块资源的使用情况。当仅有shared_cnt归零时，尽管对象已经被delete了，但仍可能有weak_ptr在观测它，程序可能需要通过这些weak_ptr（的expired方法）来确认这块内存是否被释放，因此Control Block不能被立即析构。

当理解了这一点之后，我们就能明白对Control Block的管理和对指针所指对象的管理是几乎完全不相干的两件事，因此两个计数器之间也不会互相影响。

  • 再触发node1（智能指针对象）的析构函数，node1的shared_cnt减一；

  • node1的shared_cnt此时归零，触发Node（结构体）的析构函数，node1所管理的data内存被释放，同时node1->next指向的node2的shared_cnt减一；

  • node2的shared_cnt此时归零，触发Node（结构体）的析构函数，node2所管理的data内存被释放，同时node2->prev指向的node1的weak_cnt减一。node2的shared_cnt和weak_cnt都是0也触发了node2的Control Block析构；

  • node1的shared_cnt和weak_cnt都归零，触发node1的Control Block析构。

不难发现，weak_cnt通过观察的方式实现了功能需要的相互链接，但又同时破除了shared_cnt成环导致的引用循环。

因为 weak_ptr 不控制生命周期，它不能直接解引用，但它可以通过lock()方法临时提升为 shared_ptr（会使得shared_cnt计数加一）。
